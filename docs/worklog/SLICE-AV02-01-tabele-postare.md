Facts from the data (one unit, May 2026): every document has a note (1 to 5 documents per note), every operation a document, every document an operation; every operation has debit AND credit lines and **debit = credit in all 530**; 2 operations have several debit lines and 5 several credit lines; every `SimbolCont` is in `PlanCont`, every partner code in `Parteneri`, every `CodJurnal` in `Jurnale`, every `IDClsf` in `Clasificatii`; the date of an operation equals the date of its document; `IDClsf` is empty on 169 operations. Never used (always 0 or empty): `IDSS`, `IDC`, `IdBursa`, `IDEFT`, `OP`, `NRNIR`; `Simpla` is non-zero on 5 old rows (the program writes 0). `SimbolCont` is the composed symbol of the stage-1 chart: account (7 digits) + sector-source + functional + economic classification (e.g. `401010001A650402570202`), the one `TZ_PlanCont.SimbolCont` already holds.

## Design (DDL: `sql/AVACONT/IntroducereDate/Operatii/AV02_01_operatii.sql`)

Five tables, prefix `TZ_`, in the unit database (created in `AVACONT_SURSA`, copied by the schema sync):

| New | Access | Notes |
|---|---|---|
| `TZ_NoteC` | `NoteC` | `IdNota`, `IdSubunitate`, `An`, `NumarNC`, `DataNc`; unique per subunit + year + number. The note number is given by the server (highest + 1). |
| `TZ_Documente` | `Documente` | `IdNota` (always), `NumarDocument`, `DataDocument`, `FelDocument` (free text), `Fel` (phase), `Auto`, `EditManual`, `Platit`. |
| `TZ_Oper` | `Oper` | `IdDocument`, `IdJurnal` (FK `TZ_Jurnale`), `IdClsf` (FK `Clasificatii`, NULL allowed), `IdSablon` (FK `TZ_SablonOperatii`, NULL), date, explanation, `Tip`, `Fel`, `Compartiment`, the flags `Cfpp`, `Angajament`, `Propunere`, `Ordonantare`, `Chelt`, `NrAng`, `NrOpe`, `Auto`, `Platit`. |
| `TZ_Debit`, `TZ_Credit` | `Debit`, `Credit` | `IdOper`, `IdCont` (FK `TZ_PlanCont.IdCont`: replaces the text `SimbolCont`), `IdPartener` (FK `Parteneri`, NULL: replaces the text `CodPartener`), `Suma decimal(18,2)`. |

Choices and why:
- **Keys.** Every table has its own auto-increment key. The Access ids of different files collide, so they are never keys; they are kept in `IdDocumentAccess`, `IdOperatieAccess` (and `IdSalariiAccess`, `IdxAccess`) with a unique index per parent: **the migration can run again and adds only what is missing**, and the migrated invoices (`EF_PrimiteOperatii.IdOperatie` = Access `Oper.IdOperatie`) can be pointed at the new rows.
- **Subunit.** Only the note holds `IdSubunitate`; document, operation and lines reach it through the note. The accounts of the lines must belong to the same subunit: a **server** rule (a foreign key cannot say it).
- **Deleting.** All foreign keys are `RESTRICT` (rule of stage 1: no cascade on accounting data). The server deletes lines, operations, document and note in one transaction, only with the right «Stergere N.C.» (`AV_STERGE_NC`, already designed).
- **Server rules** (not in the DDL): debit total = credit total per operation; accounts and partners exist; `NumarNC`, `NrAng`, `NrOpe` given under lock per subunit and year; no change in a closed month (the closing document `Fel = 'I'`, Access «CCV»: its exact rule to be read in stage 2).
- **Kept as free text for now:** `Documente.Fel`, `Oper.Tip`, `Oper.Fel` (`varchar(5)`). Their values mix three vocabularies (E / P / A / I; ANG / PC / PN / VA of salaries; `10`, `PC`, `V` as `Tip`). They become enumerations when the stage that writes them is ported.
- **Left out on purpose:** `AngajamentLegal`, `DataAngLeg` (FOREXE part of Access: out, operator rule 31.10.2026); `IDSS`, `IDC`, `IdBursa`, `IDEFT`, `OP`, `NRNIR`, `Simpla` (always empty, 0 or replaced); `Actiuni` (Access' own log: K-BOT has its audit journal). `Oper.IDA` (template id) is not carried: template ids of the two systems do not correspond, `IdSablon` stays NULL on migrated rows.
- **Dates (operator, 02.11.2026).** Every new table has `CreatedAt` (set when the row is made; for migrated rows the Access `DTQ`) and `UpdatedAt` (`ON UPDATE current_timestamp()`: the date of the last change). These names replace `DTQ` and `DataAdaugare` / `DataModificare` for NEW tables; the old tables are not touched (decision: no time spent changing the past). The same pair was added to `EF_PrimiteArhiva` (`sql/01EF_01_efactura_arhiva.sql`, an `ALTER ... ADD COLUMN IF NOT EXISTS` at its end, safe to run again).
- **Salaries (stage 3).** `IdSalariiAccess` / `IdxAccess` keep the link of the 34 salary documents and their operations, to be re-linked when salary tables exist.

## Migration (AVC.Migrator, step «Operatii» — WRITTEN 02.11.2026, builds clean, never run; see src/AVC.Migrator/README.md)
One step in `Avacont/…` order after Subunitati, PlanCont, Jurnale (AVC) and after `KBot.Migrator` (partners, classifications): `NoteC` -> `TZ_NoteC` (subunit of the unit through `TZ_Subunitati.IdUnitateAccess`, `An` 2026); `Documente` -> `TZ_Documente` (by `NumarNC`); `Oper` -> `TZ_Oper` (`CodJurnal` -> `TZ_Jurnale` of the subunit's sector-source, `IDClsf` -> `Clasificatii` through (`IdClsfAcc`, `IdUnitate`) as `EF_PrimiteOperatii` does); `Debit` / `Credit` -> lines (`SimbolCont` -> `TZ_PlanCont` of the subunit, `CodPartener` -> `Parteneri` of the unit). A row whose account, partner, journal or classification is missing in the target is left out and named (like the opening balances), never half written. Verification checks debit = credit per operation. The step moves operations only, **no invoice**.

## Answers of the operator (02.11.2026) and what is still open
1. **Note number per subunit and year: CORRECT** (as designed).
2. **`Cfpp` = Control Financiar Preventiv** (the preventive financial control mark). The column comment says so; it keeps default 1. `EditManual`, `Documente.Platit` and `Oper.Platit` are still «meaning to confirm».
3. **`EF_PrimiteOperatii.IdOperatie` after the migration** (the operator did not follow the question; decided here, to be corrected if wrong): the migrated invoices point at the OLD Access operation number. When the operations are migrated they get new numbers in `TZ_Oper`, so without a correction the invoices would lose their operations. The last statement of the AVC step «Operatii» replaces, in the link rows of the migrated invoices, the old number by the new one (it uses `TZ_Oper.IdOperatieAccess`; it changes only the number in the link, no invoice data), in the same transaction as the operations. The invoice migrators cannot do it: the new numbers do not exist when they run.
4. **The chain of documents (operator, 02.11.2026):** DDF / Revision (optional for revision > 0) -> the reservation change is written in FOREXE -> an accounting document appears (invoice, payroll statement, scholarship statement ...) -> accounting entry of the document -> the payment is decided -> accounting entry of the payment -> **Ordonantare** (mandatory for any payment or receipt) -> the reception is written in FOREXE -> the **order of payment** is made (single or multiple); a multiple one fills the PDF form (probably 1127, the OPME of the ministry), uploaded to FOREXE the way the CAB correction note is, and the receipt (recipisa) is obtained.

### What this means for AV02-02 (not designed yet)
- Access has `OPuri` (one line per payment order, `Oper` = the payment operation, `IDOPME`) and `OPME` (0 rows here: the header of a multiple order: `NrOPME`, `DataDoc`, `NrRec` = the receipt number, `Total`, `Platitor`, `CIF`, `Adresa`). So the model is: simple order = a line alone; multiple order = lines under a header with the PDF and the receipt.
- The order of payment is NOT only a table: it is a document with a PDF and an upload to FOREXE with a receipt, like the CAB correction note. AV02-02 therefore needs the Access forms (`OPuri2017`, OP9, OPME) and the CAB-note flow of K-BOT read first.
- Open question for AV02-02: is the **Ordonantare** of the chain the existing K-BOT ORD (`FX_ORD_*`), so that `TZ_Oper.NrOpe` / the flag `Ordonantare` must point at it, or is it a number of the accounting only?
- The rest of the chain (DDF, revision, reservation, reception) already exists in K-BOT and is not touched by AV02.

### The Ordonantare is the existing ORD (operator, 02.11.2026) and the link with the operations
Confirmed: the Ordonantare of the chain is the ORD of K-BOT (`FX_ORD` header: `NrORD`, `DataORD`, `CodAngajament`; `FX_ORD_PART`; `FX_ORD_TBL` rows: classification, partner, indicator, value). In Access there was NO link between `FX_ORD` and `Oper`: every operation had the tick `Ordonantare` and a number `NrOPE`, and the operation itself was shown as an ordonantare.
- **New column `TZ_Oper.IdOrdTbl`** (nullable, foreign key to `FX_ORD_TBL.IDORDTBLP`, `ON DELETE SET NULL`: deleting an ORD frees its operations, nothing accounting is deleted). The link is made at the ORD row, because that is where classification, partner and value are; the header comes by a join. **One ORD row = one operation** (operator's belief, 02.11.2026): the server refuses a second operation on a row that is already linked; the index is NOT unique on purpose, so the rule can be relaxed without DDL if a case of several operations on one row shows up.
- **New operations**: the payment is booked first, the ORD is made after it; the link is set when the ORD is made (the ORD window will offer the unlinked operations with `Ordonantare` of the same supplier and classification). Designed in AV02-02.
- **The two numbers are separate (operator, 02.11.2026).** `NrOpe` of the operations was made in the correct (date) order; `NrORD` of K-BOT is most probably in the order the ORDs were made, not in date order, and the two series are NOT the same. So `TZ_Oper.NrOpe` stays the accounting number (migrated as it is, given by the server in date order per subunit and year) and is never copied from `NrORD` or compared with it. Once an operation is linked, the accounting number of the ordonantare is read FROM the operation. Whether `FX_ORD.NrORD` of a linked ORD should ever be rewritten with it is open (an ORD already loaded or signed — `Incarcat`, `Semnatura` — cannot change its number); until decided, `NrORD` is not touched.
- **Operations migrated from Access**: they are matched with the ORD rows of the unit by a rule that writes only when the match is sure and reports the rest (like the automatic link of invoices to receptions, 00EF-38): operation with `Ordonantare` + same classification + same partner + same value + same year; **the numbers are not used at all**. When several operations and several ORD rows have the same classification, partner and value, the match is ambiguous (the order of the two series cannot break the tie): reported, not written. Counts «linked / ambiguous / none» in the verification; nothing is written for the last two.
- **Answered**: the Access `NrOPE` is NOT the `NrORD` of K-BOT (operator: «nu ne putem baza pe asta»). (b) is answered (one row = one operation), so the migration of the link may WRITE the sure matches (an operation and a row that are each other's only candidate); ambiguous and unmatched ones are only reported. Equal groups (the same classification, partner, value and year on k operations and k rows) are not tied by number. **Second criterion (operator, 02.11.2026): the month of the operation = the month of the ORD (`DataORD`).** It is used to NARROW a group that is ambiguous without it (so a legitimate match across a month boundary is not lost when the pair is already unique); a group that stays ambiguous after the month is reported, not written. If the report still shows many, a tie-break by date (the operation not after its ORD) can be added.
- **Renumbering the ORDs (operator, 02.11.2026).** No document is signed so far, so `FX_ORD.NrORD` of the linked ORDs MAY be replaced by the accounting number. That will be an **option of KBotAdmin**, applied by the operator when and if she wants; the application never does it by itself and AV02 does not touch `NrORD`. Not built; it needs the links first (migration of the links, then this option). Nothing is open for the operator in this section.
