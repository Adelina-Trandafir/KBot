# SLICE-01EF-07 — «Contari»: the page laid out like the Access form, started from the invoice menu

Operator's request (04.11.2026), with a screenshot of the Access form as the model. Numbers 01EF-05 (payment save) and 01EF-06 (year carry-over) stay reserved; this is 01EF-07.

## What changed and why
1. **Layout (the screenshot).** `PrimiteContarePage` rebuilt in the Designer: four headed fields on top (**Clasificație bugetară**, **Cod Client**, **Cont IBAN**, **Fel factură (pentru O.P.-uri)**); **Documente evidențiere** (list of templates) + the evidence grid (NC, Document, Fel, Data, Valoare rămasă de înregistrat, Valoare care se plătește; totals in the footer); **Documente plată** + the order of payment (NC, Dată, Număr OP, Explicație O.P., Valoare); **Renunță** left, **Salvează** right. The two template combos and the note combo are gone: the templates are one-column `KBotDataView` lists (a click chooses; a click on the chosen payment template takes it off); the note is the **NC** combo column of both grids (one note for the whole save, so every NC cell shows the same value; an existing number from the list or a typed new one).
2. **Start from the menu.** Right-click on an invoice (window with all invoices) → **«Adaugă operații contabile»** (`MenuContare`): everything ticked before is dropped, the invoice is ticked, the page is shown and the evidence grid filled with it. **Only the invoices of the same supplier** get tick boxes now; the suppliers have none (`ContareBox` / `ApplyContareBoxes` in `PrimiteView.Contare.vb`; the boxes appear when the supplier is set, without rebuilding the tree).
3. **Order of payment awake only with a payment template.** The server no longer picks the single payment template on its own (`primite_contari.py`); `gridPlata` is disabled and empty until one is chosen. The value is the sum of the values to pay; the Number OP is a digits-only cell.
4. **Ticking more invoices.** Each tick adds a row to the evidence grid, each untick removes it (the server recalculates as before); **at least one invoice stays ticked** (the last untick is put back, with a notice; «Renunță» clears all). In the order of payment ONLY the value and the explanation change; the note, the date and the number typed stay. The explanation is `F <numbers> C <client code> <FelOP of the template, when it has one>`; «Fel factură» shows the template's `FelOP` (new `plata.FelOP` in the answer) and can be edited.
5. **Explanation length bar.** `KBotProgressBar` under the order grid, tied live to the length of the explanation: 1..75 (official limit; the old 69 yellow / 254 limits are gone), red when empty, amber from 70, with «n / 75». «Salvează» also needs ≥ 1 character while an order of payment is being made.
6. **ASCII, no comma (order of payment).** `OpExplicatie` (KBot.EFactura): diacritics → plain letters (NFD, marks dropped), typographic quotes/dashes → ASCII twins, **comma → space**, other non-ASCII dropped, single spaces, cut at 75. Applied while typing (new grid event `EditorTextChanged`), at commit (`CellValidating`), to «Cod client» and «Fel factură», and to the text the page composes. The server has the same rule (`text_op` in `primite_contari.py`) for the explanation and `FelOP` it sends, ready for the future save.
7. **Warnings.** The page has no free space for the long blocks of the old layout: the footer between the buttons shows the supplier and the most serious warning (+ how many more); everything else (all warnings, angajament/indicator, next note number, the bookings the templates would produce) is in its tooltip.
8. **Save.** Still evidence only. When an order of payment is on the page, «Salvează» asks «Plata nu se înregistrează încă … Continuați?» (Yes/No) so nothing looks saved that is not.
