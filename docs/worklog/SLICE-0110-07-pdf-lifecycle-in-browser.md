# SLICE-0110-07 - research: can the web area show the LiveCycle (XFA) PDFs? (operator request, 05.10.2026)

A spike, as planned: a verdict with evidence, no feature. Nothing in the repository's code changed; the throw-away
probes lived in the session scratchpad. The only repository edit is the `pdf-stub` entry added to `.claude/launch.json`
(dev preview config, same kind as the other stub entries).

## Verdict
**Yes, it is feasible, with an ordinary open-source viewer (pdf.js) and no server-side conversion.** Two different kinds of
file exist, and they behave differently:

| File | What it is | Plain viewer (pdf.js without XFA, same as a browser's own) | pdf.js with `enableXfa: true` |
|---|---|---|---|
| Unsigned, as XfaWriter writes it (`DDF_V008…`, `ORD_V011…`, the Fundamentare sample) | **pure dynamic XFA 3.0**: one page that only says «Please wait... If this message is not eventually replaced…» (`/NeedsRendering true`) | only the «Please wait» page - this is what the operator saw | **renders the real form**: 4 pages for the DDF, 2 for the ORD, tables with the repeating rows from the data (ORD sample: the 1111 / -1111 rows appear) |
| Signed in Adobe (`Etapa1_Semnata`, `Etapa3_Semnata` with 8 signatures, `NOTA CAB 23` with 6) | Adobe writes the **rendered pages into the file when it signs** (incremental revisions, the newest datasets win) | **renders correctly**: final values, e.g. «aaaaa», CIF 21015411, 30.09.2026, the IBAN, the corrected note's 2 rows | same picture |

pdf.js picked the newest data revision on its own: `Etapa1` and `Etapa3` show different numbers in the table, as they should.

## Why this matters for the server
`routes/forexe/pdf.py` stores only SIGNED PDFs (unsigned ones are regenerated by the desktop app). So the files the web area could
list are, in the common case, the first kind of row above - already readable by any PDF viewer. The pdf.js XFA engine is the safety
net for a file that is still pure XFA.

## What was measured
- Sample probe (raw parse, no PDF library on this PC): all samples have `template` XFA 3.0 with `pageSet`, `layout="tb"`/`row`/`table`,
  repeating sections (`occur max=-1`), 79-101 scripts, `/NeedsRendering true`; the signed ones also carry 4-8 `/ByteRange` signatures.
- Browser pane, pdf.js 4.10.38 from a CDN on a scratch page (`PDFViewer` with `enableXfa`): every sample above, each with XFA on and off,
  text and pictures compared.
- Cost of shipping it ourselves (the pages allow scripts only from this server): `pdf.min.mjs` 353 KB, `pdf.worker.min.mjs` 1.38 MB,
  `pdf_viewer.min.mjs` 155 KB, `pdf_viewer.min.css` 85 KB (uncompressed, ~2 MB; Apache-2.0).

## Limits you should know before promising it
1. **A picture, not a verification.** The page shows what the document looks like; it does not check the digital signatures
   (the desktop app and Adobe do that). The page should say so.
2. **pdf.js does not run the form's scripts** (79-101 of them). Values that the document computes on opening (not present in the data)
   may differ from Adobe's. In the ORD sample the totals came from the data, so they showed; a document that relies on a script for a
   total would need a look.
3. **Layout is pdf.js's, not Adobe's**: close (tables, sections, repeating rows right), page breaks and fine spacing can differ.
4. **Fields are live inputs in the XFA layer** (they look editable). A viewing page must make them inert (`pointer-events: none` on
   `.xfaLayer`, or disabled inputs) - not done in the spike.
5. **Not tested**: a final signed DDF produced by K-BOT's own signing flow (no such file in the repository; the signed samples here come
   from Adobe by hand), attachments inside the PDF (the «Ataseaza fisiere» content), very large documents, phones.
6. Whether Chrome's built-in viewer shows the signed files too was not tested (the pdf.js plain mode is the closest proxy).
